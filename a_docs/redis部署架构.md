# redis部署架构
- 单节点
- 主从复制:一主多从，写主独从，提升读性能，同时实现数据热备份。
- 哨兵模式(Sentinel): 基于主从复制，新增哨兵集群。监控主从节点，主节点故障时自动故障转移保障高可用。
- 集群模式(Cluster): 多主多从分片，数据按哈希槽拆分到不同主节点。可横向部署。
- Proxy模式：通过Proxy中间件(Twemproxy、Codis)管理后端Redis节点。客户端统一接入Proxy,不需要关心集群细节。


# 不同部署架构优缺点

｜-- ｜-- ｜-- ｜-- ｜-- ｜-- ｜-- ｜-- ｜
单机版	结构简单、无额外开销	开发 / 测试环境、低并发非核心业务、临时存储	部署维护便捷、延迟低、无数据同步损耗	无高可用、并发上限低、单点故障风险高	极低	强一致	无（仅垂直扩容）
主从复制	读写分离、数据备份	读多写少场景、需数据备份但对故障转移无要求	提升读性能、支持数据热备、部署简单	主节点故障需手动切换、不支持写扩容	低	最终一致	读扩容（加从节点）
哨兵模式	自动故障转移、高可用	生产环境中小规模业务、需高可用无分片需求	无需手动干预故障、兼容主从架构、轻量	不支持数据分片、写性能受主节点限制	中低	最终一致	读扩容（加从节点）
集群模式	分片存储、高并发高可用	生产环境大规模业务、高并发高容量需求	支持水平扩容、并发能力强、故障自动恢复	部署维护复杂、跨槽操作有额外开销	中高	最终一致	高（增减主从节点）
Proxy 模式	客户端透明、集群统一管理	需兼容旧客户端、复杂集群运维场景	隐藏集群细节、支持多种后端节点组合	新增中间件开销、Proxy 可能成性能瓶颈	中高	最终一致	中（后端节点扩容）
